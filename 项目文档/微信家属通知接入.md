# 超时未开盒 → 微信家属通知

## 已确认的核心目标

用户在 2026-11-05 明确：核心是药盒在规定时间内没有被打开时，通知微信小程序中的家属；希望关闭小程序也能收到微信通知。

正式流程应为：家属设置计划 → 到点由药盒提醒 → 磁簧开关检测实际开盒并上传 → 后端按截止时间检查是否收到有效开盒记录 → 超时生成家属提醒 → 通过微信订阅消息提交给已授权的家属。

“移开磁铁让蜂鸣器响三次”只用于硬件检测联调，不是正式业务。蜂鸣器的正式用途是到用药提醒时间后提醒使用者；家属通知由持续运行的后端负责，不依赖小程序页面一直打开，也不新增设备心跳。

## 当前能力与尚未验证的部分

- 原后端已每 5 秒独立推进时间规则，并生成、去重应用内提醒。新通知派发任务与时间规则任务分开运行，微信网络较慢时不阻塞时间推进。
- 已新增小程序“提醒 → 微信提醒 → 开启微信提醒”入口。用户主动选择允许后，小程序取得临时登录 code，服务端向微信核验并绑定接收者；不信任客户端声称的 openid。
- 已新增服务端配置校验、订阅授权估计次数、持久化去重发件箱、发送结果和失败状态。不把 HTTP 超时当作发送成功，也不盲目重发不确定结果。
- 演示账号和软件模拟来源的提醒不会发送真实微信消息。未配置时仍保留原有应用内提醒，不会调用微信发送接口。
- 尚未配置实际 AppSecret、获批模板与字段并在真机完成授权、通知接收验证。接口返回成功仅代表微信受理，不代表手机已显示或家属已读。
- 2026-11-08 已完成独立例程下门磁读数、蜂鸣器三声/停铃及 OLED 显示的短时实物验证；真实开盒事件上传和微信手机接收仍待闭环联调。2026-11-09 新写的本地 08:00/09:00 定时程序尚未烧录，未改变本文原有服务端时间规则，详见[硬件接入进度总结](硬件接入进度总结.md)。

## 保留的时间规则

本次没有改动已有规则：从计划开始时间起设 30 分钟提醒窗口，窗口内每 10 分钟计一次提醒、最多 3 次；窗口结束 15 分钟后才生成家属提醒。

例如仅用于说明：08:00 的计划，窗口为 08:00～08:30，若仍未收到开盒记录，08:45 起进入家属提醒流程。是否需要改为窗口结束立即通知，应另行确认，不能把现有 15 分钟宽限静默删除。

后端依据“未收到有效开盒记录”判断，无法仅凭没有记录确认老人实际没有操作。服务器持续运行是定时判定和通知的条件；当前规则不会在次日自动补发前一天整天停机期间遗漏的提醒。

## 在本机配置微信服务

1. 确认当前小程序账号实际有可用的订阅消息模板及对应权限；以该账号微信后台可配置的内容为准。一次授权不应被理解为永久无限通知，持续通知能力需要核对实际模板和授权规则。
2. 将 [backend/.env.example](../backend/.env.example) 复制为同目录 `.env`。真实密钥只在本机填写，不发聊天，不放入小程序前端。
3. 填写与当前小程序一致的 `WECHAT_APP_ID`、服务端 `WECHAT_APP_SECRET`、实际模板的 `WECHAT_OVERDUE_TEMPLATE_ID`。
4. 根据模板中真实字段填写 `WECHAT_OVERDUE_FIELDS`，必须映射 `name`、`time`、`remark` 三项。目前支持姓名或事项字段、时间字段、事项字段。例如 `{"name":"thing1","time":"time2","remark":"thing3"}` 仅是格式示例，真实模板字段可能不同。
5. `WECHAT_MINIPROGRAM_STATE` 与测试版本对应：正式 `formal`、体验 `trial`、开发 `developer`。
6. 重启主项目后端。服务端会读取 `backend/.env`；已设置的进程环境变量优先。不需要、也不能把 AppSecret 填进 `微信小程序/utils/config.js`。
7. 家属使用自己的注册账号进入小程序“提醒”页面，主动点击“开启微信提醒”并允许订阅。演示账号只展示软件效果，不订阅真实通知。

当前一个微信接收者只绑定一个家属账号，避免不同家庭间误发；多个接收人、长期订阅类型和额外通知渠道尚未扩展。

## 配置与状态接口

- `GET /api/notifications/wechat`：家属会话认证，返回配置可用性、模板 ID、授权次数估计及最近发送状态；不返回 openid、AppSecret 或 access token。
- `POST /api/notifications/wechat/authorize`：家属会话认证，正文仅为 `code` 和 `templateId`；服务端核验微信身份，同一个 code 不重复增加估计次数。
- 订阅弹窗必须从用户点击直接发起。授权选择完成后再进行微信登录和后端请求，不能先等待后端请求再尝试弹授权窗。
- `sent`：微信明确受理，不是送达回执。`unknown`：发送是否受理无法确定，不自动重发。`needs_authorization`：微信明确要求重新订阅。`cancelled`：任务已处理、已取消或过期，不再发送。

## 实物验收顺序

1. 单独验证门磁靠近和移开时 GPIO33 有稳定变化，完成关盖电平校准。
2. 验证蜂鸣器 D25 控制和到点提醒，再实现设备对当前演示计划的真实开盒上传；网络重试沿用同一 eventId 和正文。
3. 在隔离测试家庭中验证“窗口内开盒 → 不产生该次超时通知”和“截止后无开盒记录 → 后台自动判定”。
4. 配置并授权后，关闭小程序，在后端持续运行条件下验证真实微信通知；再核对重新开盒后的取消处理、重复判定去重及授权不足提示。

当前阶段不要把“页面有一条提醒”“微信接口已受理”和“家属手机已实际收到”当作同一件事。开盒也不能作为已核实服药的证明。

## 已完成的离线验证

2026-11-05 已通过 22 项 Python 回归检查（8 项原后端业务、12 项微信通知、2 项小程序模板结构），以及微信授权/页面状态、原登录流程两组 Node 检查。通知测试用临时数据库和模拟微信接口，覆盖关闭页面后后台仍可判定与派发、用户隔离、重复授权和提醒去重、已开盒取消、授权不足、发送失败和不确定结果处理。

这些结果不代表真实微信模板已配置或手机已收到消息；没有在本次检查中向真实家属发送通知。
